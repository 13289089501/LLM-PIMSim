1. 模块概述
1.1 模块目的

Performance Model负责根据：

Operator
Hardware
Data
Interconnect

等信息，估算一个任务的执行时间。

它不负责决定：

“什么时候执行”。

而负责回答：

“如果在这个硬件上执行，这个任务需要多长时间？”

1.2 性能模型的核心思想

LLM-PIMSim不采用单一公式：

T=
Peak Compute
FLOPs
	​


因为这会严重高估真实性能。

一个算子的实际延迟至少受到以下因素影响：

Operator
   │
   ├── Compute
   │
   ├── Local Memory Access
   │
   ├── Inter-device Transfer
   │
   └── Data Dependency

因此系统采用：

计算模型 + 存储访问模型 + 数据搬运模型 + 调度等待模型

共同构成最终性能。

2. 性能模型与调度模型的边界

这是必须明确的。

Performance Model负责
算子执行多久？

数据读取多久？

数据写入多久？

设备间传输多久？
Scheduler负责
算子什么时候可以开始？

需要等待哪些数据？

需要等待哪个硬件？

多个依赖什么时候全部完成？

因此：

Performance Model→Duration

而：

Scheduler→Start/End Time

46. 一个需要特别保留的设计决策

目前我们的模型实际上已经形成了一个非常重要的体系：

                 "算得多快"
                      │
                      ▼
                Compute Model


"本地数据访问多快" ──→ Memory Model


"数据跨设备移动多快" → Transfer Model


"为什么不能马上算" ──→ Dependency Model


"什么时候真正执行" ──→ Scheduler

这几个概念必须保持独立。

否则以后分析PIM论文时，很容易把：

计算瓶颈、内存带宽瓶颈、互连带宽瓶颈、同步等待

混成一个“Memory Bound”。

而这恰恰会削弱这个模拟器的研究价值。
