《06_离散事件调度模块设计文档》

项目：LLM-PIMSim
模块：Discrete Event Scheduler（离散事件调度模块）
版本：v1.0

1. 模块概述
1.1 模块目的

Scheduler是整个LLM-PIMSim的执行控制中心。

前面的模块解决：

模块	解决问题
LLM Model	模型有哪些计算
Operator Model	计算如何拆分
Data Model	数据是什么
Placement Model	数据在哪里
Hardware Model	硬件有什么能力
Performance Model	执行需要多久

而Scheduler解决：

这些任务按照什么顺序，在什么时候，在什么硬件上执行。

1.2 为什么采用离散事件模拟

目前模拟器采用：

Discrete Event Simulation（离散事件模拟，DES）

而不是简单公式累加。

简单公式模型

例如：

假设：

Layer1

↓

Layer2

↓

Layer3

直接：

T=T
1
	​

+T
2
	​

+T
3
	​


问题：

无法处理：

多计算模块并行
数据等待
数据搬运
权重驻留
多输入同步
离散事件模型

系统状态随着事件变化：

例如：

0ms

GPU空闲

DRAM-PIM计算完成


5ms

Weight Transfer完成


8ms

FFN开始


10ms

FFN结束


模拟器只关心：

“什么时候发生了什么事情”。

4. 为什么需要事件(Event)

Scheduler不直接执行：

run(operator)

而是生成：

Event

原因：

真实硬件执行过程：

不是：

任务A结束

↓

任务B开始

而是：

计算事件

数据搬运事件

等待事件

同步事件


共同组成时间线。

10. Operator执行流程

一个Operator进入Scheduler后：

Step 1

检查依赖。

例如：

Attention：

需要Q,K,V

检查：

for data in input:

    if data.ready_time > current_time:

        wait
Step 2

检查数据位置。

例如：

Weight:

DRAM-PIM

但是：

执行：

GPU

发现：

位置不同。

生成：

Transfer Event
Step 3

等待Transfer完成。

更新：

Weight.ready_time
Step 4

生成Compute Event。

13. 权重加载机制设计

你之前提出：

用户需要先决定权重加载进哪个模块。

这个设计保留。

原因：

不同论文：

核心差异就是：

weight placement。

因此：

初始化阶段：

执行：

Placement Configuration

↓

Load Weight

↓

Initialize Data Location


例如：

配置：

{
"FFN_weight":

"DRAM_PIM0"
}

模拟开始：

FFN Weight

location=DRAM_PIM0

Scheduler：

不负责决定：

“权重放哪里”。

Scheduler只负责：

“按照这个决定执行”。

"DRAM_PIM"

}

原因：

优化目标

未来：

可以增加：

例如：

目标：

16. 调度策略

第一版：

采用：

Dependency-aware Greedy Scheduling

即：

满足依赖后：

立即执行。

流程：

寻找Ready Operator

↓

寻找Available Hardware

↓

执行


优点：

简单。

符合第一版研究目的。

17. 为什么不采用复杂调度算法

暂不考虑：

ILP
Reinforcement Learning
Genetic Algorithm

原因：

我们的目标：

不是寻找最优调度。

而是：

分析：

某种PIM架构为什么快/慢。
