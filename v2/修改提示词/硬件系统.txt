我设计了一个系统，用以计算LLM在不同设备上的推理延时
其核心部件有两个：硬件系统和算子系统。我将LLM模型拆成多个算子，放在不同硬件上跑出延时，现在我需要对硬件参数进行调整，使其更加逼近真实情况。

我使用以下逻辑来计算延时：
整个模拟的延时其实分两层：性能模型（performance.py）给出每个算子的时间尺度，调度器（scheduler.py）把这些时间累加并推进仿真时钟，最终总延时 = 最后一个完成的算子事件结束时刻。

具体分三部分算：

计算时间 compute_time_ns（performance.py:29）
T_compute = FLOPs ÷ (PeakFLOPS × 算子效率)，再 ×1e9 转成纳秒。其中 PeakFLOPS 取硬件的 peak_compute_flops（一个统一高峰算力），效率 efficiency_for(op.op_type) 从硬件的效率表按算子类型查。若 FLOPs、峰值或效率任一为 0，则直接返回 0（视为纯内存/同步类算子）。
本地读写时间 local_read/write_time_ns（性能模型里是纯延迟公式）
T_local_rw = latency_ns + data_size_bytes ÷ 带宽，再 ×1e9。即固定访问延迟 + 按带宽换算的数据传输耗时；数据量 0 或带宽 0 时直接返回固定延迟。读用硬件的 read_bandwidth，写用 write_bandwidth（读写带宽独立、可不对称）。
跨设备搬运时间 transfer_time_ns
src→dst 搬一次数据 = T_read(src本地读) + T_link(src→dst 链路) + T_write(dst本地写)。链路传输段用 Link.latency_ns + data_size ÷ 链路写方向带宽 ×1e9；注意它对 src→dst 方向用的是链路的 write 带宽通道（数据流方向占用的通道），若没有直连链路则返回 0 由调度器告警。
最后调度器 _schedule_op 做三件事：把每个输入"搬运到目标硬件就绪"的时刻（各输入取最晚到达）作为起点，算出单算子总耗时 compute_dur（其中 _ensure_data_at/搬运事件贡献 transfer_ns，等数据导致 sync_ns），然后 start_ns = max(当前仿真时钟, 该硬件空闲时刻, 所有输入最晚就绪)，end_ns = start_ns + compute_dur，把 COMPUTE 事件推入离散事件队列并让该硬件忙到 end_ns。整个 DAG 按数据依赖逐级执行，最后一个算子事件落地的 end_time_ns 就是总延时（result.total_latency_ns），并可拆成 compute / local_read / local_write / transfer / sync 五类累加为 DurationBreakdown。

为了获取更真实的硬件参数，你应该采用真实实验倒推的方法，具体来说如下：1、找到使用对应硬件的论文，通过实验结果倒推设备参数，这样可以考虑到真实环境而非理想数值。2、阅读对应模型的论文，直接提取关键参数。稍等我会给你硬件的参数清单，你需要找到对应论文然后告诉我参数。

我们所有实验全部基于llama7b模型搭建，因此你需要找有关这个模型的论文。

现在我们支持五种硬件结构：CPU，GPU，SRAM-PIM，DRAM-PIM，RERAM-PIM。每种硬件需要如下参数：峰值算力，存储容量，读带宽，写带宽，读延迟，写延迟，对算子的效率（这个稍后等算子阶段再做），支持的精度。
