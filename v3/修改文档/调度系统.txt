=== agent回答 ===
下面把当前"总延时是怎么算出来的"完整算法讲清楚（实现位于 core/engine.py）。

一、时间怎么定刻度
- 所有时间用纳秒 ns；时钟不是逐 ns 走，而是**跳变**：每次从事件队列弹出"最早结束的事件"，把全局时钟拨到该事件的结束时刻再处理。这就是离散事件调度(DES)。

二、单算子的三段耗时（性能模型 PerformanceModel）
调度前，对每个"准备跑"的算子，用硬件参数算三部分：
1) 计算耗时（compute）： T_c = op.flops / (hw.peak_compute_flops × efficiency[op.op_type])，单位换算成 ns
   —— efficiency 就是硬件对不同算子类型的利用率（见硬件系统）。
2) 跨设备搬运（transfer）：为了让该算子的每个输入到位，若输入数据不在目标硬件上，
   要搬过来，耗时 T_t = T_read(源本地读) + T_link(源→目标链路的 write_bw) + T_write(目标本地写)。
   若输入已在目标硬件（驻留命中）就不搬，搬运=0。
3) 同步等待（sync）：不是算子自己的动作，而是"为了让输入/设备空闲对齐而等的时长"。

三、调度器的就绪判定（何时能开跑）
一个算子满足以下全部条件才从 WAITING→READY：
- 所有输入数据都有副本已就绪（数据状态表 DataStateTable 维护每个数据在哪个设备何时就绪）；
- 若输入是"被切分的权重"，必须**全部切片**都在各自设备就绪（ALL-GATHER 语义，缺一片不能跑）；
- 有目标设备（compute_map 里有映射），且该设备能执行该算子（效率/精度/类别兼容）。

四、算子开跑的时间（Dependency + 资源对齐）
设：
- clock = 当前全局时钟
- free_at = 目标设备当前最早空闲时刻（设备串行，同一时刻只能跑一个算子）
- max_arrival = 该算子所有输入数据到达目标设备的最晚时刻
则：
  start = max( clock, free_at, max_arrival )
  end   = start + compute
设备在 [start, end) 被占用，其他算子看到它 busy_until=end。
同步等待 sync = max(0, max_arrival - max(clock, free_at))，即"等数据 或 等设备"。
（说明：真正的同步等待，是当 max_arrival 主导时，设备其实已空闲、纯粹等数据到位的那段。）

五、总延时
事件循环结束（队列空、所有可算子都跑完）后：
  total_latency = max(end_ns over all operators) ，即最后一个算子结束的时刻。
若存在永不就绪的算子（数据永远到不了/精度不支持/未映射），它们会一直停在 WAITING，
不进入 op_timings，所以总延时只反映"能跑的算子"——这正是输出系统里 diagnostics（完成度）
要暴露的问题来源。

六、分解统计
- compute(总) = Σ 各算子 compute
- transfer(总) = Σ 各算子为取输入的搬运耗时（transfer_events 里累加）
- sync(总)     = Σ 各算子 sync
- 瓶颈类型 = 三者里最大（COMPUTE/COMMUNICATION/SYNCHRONIZATION），这是简化归因
  ——真正的瓶颈应该是"这条关键路径上的最长环"，建议后续做关键路径(CPM)归因，见下。

—— 建议改进点（待商讨）——
1) 目前"瓶颈"用总量最大者近似；更准确的做法是算**关键路径**：找出 end 时刻最晚且对延迟贡献最大的那串算子，给出"哪条链决定了总延时"。这更适合论文级的瓶颈分析。
2) 目前每个算子一次只在一个设备上串行跑（单资源占用），没有模拟**算子内并行度/多核/分片并行**（parallelism 字段存在但未真正用于拆分执行时长）。若要贴近"并行加速"，需要把 parallel 参数纳入 compute 公式。
3) Decode 逐 token 的动态 KV 目前没进调度（前面算子系统也提到），一旦做展开，调度循环会按 token 推进，KV 增长自然体现。
4) 设备在 transfer 期间是否被占用、链路带宽是否被多条并发搬运共享，目前是简化模型（每趟搬运独立计时、未做带宽抢占）。若要精确，需加"链路视为共享资源"的占用与排队。

以上是当前延时算法的完整描述与改进方向，供确认。

【A. 双宏观参数落实 KV 建模（input_tokens / generate_tokens）】

  - experiment.yaml 的 workload 段新增/统一用 input_tokens + generate_tokens（不再用含义不清的 decode_steps）；
  - 算子系统 WorkloadBuilder：KV 相关算子不再只保留 cost_fn 的 Range，而是把 KV 终点(或逐 token 求和)

  - WorkloadAdapter：执行层对 KV 相关算子使用反映 KV 增长的参数（不再只用 compute_flops_min 代表值）；

  - 调度内核新增"算子切片分派"：compute_map 支持算子 → 多设备列表；调度把算子按切片拆分到各设备；
